=== why this file is named insecure-skip ===
The guard is the first condition of the snippet: outside a secure context the
register call is unreachable — the browser registers NOTHING and, by design,
logs nothing (silent skip; the .catch(function () {}) keeps even a failed
registration silent). That is the documented T208 trade-off: on an insecure
origin (a plain-HTTP LAN address, or TLS with an untrusted self-signed cert —
the deployment scenario of plan section 8) window.isSecureContext is false, the
PWA affordances are skipped and the app keeps working as a normal web page.
Full PWA on a LAN needs a trusted cert (ACME or a Tailscale cert) — an ops
decision, not code.

Plan clause mapping: 'an insecure origin must log the skip reason and register
nothing'. Register-nothing is proven above statically (the register call is
behind window.isSecureContext). The client deliberately does not log to the
console (silent skip, per the T208 decision); this file IS the recorded skip
reason.

Precision note on THIS QA origin: the kernel answers here as
http://localhost:18443 (plain HTTP, no jhin.security -> no TlsProvider). There
is no browser in this environment, so the snippet is never executed here at
all (browser-unavailable.txt) — the skip is proven on the served bytes. A
browser pointed at a plain-HTTP non-loopback origin (the plan's LAN case)
would evaluate window.isSecureContext === false and skip exactly as designed;
note that modern browsers treat http://localhost (loopback) itself as a
secure context (Secure Contexts spec, potentially-trustworthy origin), so on
this exact QA URL a real browser would attempt the registration — silent
either way thanks to the guard plus the empty catch. On a real https origin
with a trusted cert the same snippet registers /sw.js.
